# B9 — حالة السائق تبقى `online` بعد انقطاع السوكيت

- **التاريخ:** 2026-09-12
- **الملف:** `sockets/driver.socket.js:404-406`
- **الخطورة:** 🟠 عالٍ — يهدر جولات البحث عن سائق ويؤخّر الطلبات

---

## المشكلة

معالج الانقطاع يسجّل سطراً في السجل ولا يفعل شيئاً آخر:

```js
socket.on("disconnect", () => {
  console.log("Driver disconnected:", driverId);
});
```

فإذا سقطت شبكة السائق، أو أُغلق التطبيق، أو قتله النظام، تبقى `availability` في قاعدة البيانات `online`.

## الأثر

`order.service.js:80` يبحث عن السائقين بـ`availability: "online"` ويرسل العرض إلى غرفة السائق.
السائق المنقطع ليس في الغرفة، فلا يصله شيء ولا يستطيع الرد:

- تُحجز جولة عرض كاملة لسائق غائب حتى تنتهي مهلتها.
- الطلب يتأخر على الزبون بمقدار جولة (أو أكثر إن كان أكثر من سائق في الحالة نفسها).
- لوحة الأدمن تعرض سائقين «متصلين» وهم غير متصلين فعلياً.

هذا يتفاقم على شبكات الهاتف المتنقلة حيث الانقطاع القصير أمر طبيعي.

## إعادة الإنتاج

1. سجّل دخول سائق وفعّل «متصل» ← `availability = "online"`.
2. أغلق التطبيق تماماً أو فعّل وضع الطيران.
3. اقرأ السائق من قاعدة البيانات:

```js
db.drivers.findOne({ _id: ObjectId("<id>") }, { availability: 1, updatedAt: 1 })
// ← availability: "online" رغم انقطاع الاتصال
```

4. أنشئ طلباً في منطقته ← تُهدر جولة البحث عليه.

## الإصلاح المقترح

إعادة الحالة إلى `offline` عند الانقطاع، مع استثناء السائق الذي يحمل طلباً نشطاً (حالته `busy`
ويجب ألا تتحول إلى `offline` لأن الطلب ما زال مسنداً إليه):

```js
socket.on("disconnect", async () => {
  console.log("Driver disconnected:", driverId);
  try {
    const activeOrder = await Order.findOne({
      driverId,
      orderStatus: { $in: ["picked_up", "on_the_way"] },
    }).select("_id");

    // السائق الذي يوصّل طلباً يبقى busy — انقطاعه مؤقت ولا يُلغي الإسناد
    if (activeOrder) return;

    await Driver.findByIdAndUpdate(driverId, { availability: "offline" });
  } catch (err) {
    console.error("disconnect cleanup failed:", err);
  }
});
```

**ملاحظة عن إعادة الاتصال:** التطبيق عند عودة الشبكة يعيد المزامنة مع السيرفر ويقرأ الحالة الحقيقية،
ثم يُظهر للسائق أنه أصبح غير متصل ليعيد التفعيل بنقرة. إن فضّلتم بدل ذلك إعادة `online` تلقائياً عند
إعادة الاتصال، نحتاج حدثاً صريحاً منكم لنعتمد عليه بدل التخمين — أخبرونا بما تفضّلون.

## من جهة التطبيق (منفَّذ)

- مؤشر الحالة في الشاشة الرئيسية صار يميّز ثلاث حالات: رمادي (غير متصل أو جارٍ المزامنة)،
  أخضر (متصل والقناة سليمة)، **برتقالي** (السيرفر يقول `online` لكن السوكيت أو GPS مكسور)،
  مع تحذير صريح «لن تصلك طلبات الآن».
- مصدر الحقيقة الوحيد للحالة صار ردّ السيرفر (`dirver-info` + `driver:currentStatus`)، بلا أي
  تحديث متفائل محلي.
- قفل يمنع تبديل الحالة المتسابق عند النقر السريع، مع انتظار تأكيد `driver:currentStatus` بدل
  تأخير ثابت.

# ردّنا على رفضكم (2026-09-13)

نقبل سحب الإصلاح بصيغته المقترحة — كنتم محقّين في نقطة جوهرية. لكن **التبرير نفسه غير صحيح**،
وقد فحصناه في كودكم سطراً سطراً.

## ما نوافقكم عليه

قلب الحالة إلى `offline` عند كل `disconnect` خطأ فعلاً: الانقطاع القصير سلوك عادي على الموبايل،
و`offline` تُخرج السائق من `find({ availability: "online" })` فيفقد حتى إشعار الإيقاظ. سحبنا الاقتراح.

## ما لا نوافقكم عليه: FCM ليس قناة تسليم للعرض

«القناة الثانية» جرس إيقاظ لا قناة عرض. الأدلة من كودكم أنتم:

1. **حمولة الإشعار = `{orderId, orderNumber, timeoutSeconds: "30"}` فقط**
   (`sockets/services/drivernotification.service.js:20-24`). بلا اسم مطعم أو عنوان أو أصناف أو سعر
   أو أجر السائق — لا يمكن بناء شاشة العرض منها.
2. **لا يمكن جلب الباقي عبر HTTP:** `getOrderDetails` يستعلم
   `Order.findOne({ _id: orderId, driverId })`، والطلب أثناء العرض غير مُسنَد لأحد بعد، فالرد **404**.
3. **لا إعادة إرسال عند عودة السوكيت:** معالج `connection` (`sockets/driver.socket.js:20-27`) يبثّ
   `driver:currentStatus` فقط. و`pendingDriverIds` تُستخدم للسحب والإلغاء، ولا تُقرأ أبداً لإعادة الإرسال.
4. **القبول نفسه يحتاج سوكيتاً حياً:** التطبيق يرسل `order:driverResponse` عبر السوكيت حصراً.

**النتيجة العملية:** السائق الذي انقطع سوكيته أثناء الجولة يستلم إشعاراً يوقظ التطبيق، ثم لا يجد أي
عرض — ولو وجده لما استطاع قبوله. والجولة (٣٠ ثانية) تُستهلك عليه فعلاً، وهو ما وصفناه في الملاحظة الأصلية.

ولاحظوا أن التطبيق مكتوب أصلاً على افتراض أنكم تعيدون الإرسال: عند وصول الإشعار يستدعي
`ensureConnected()` وينتظر `order:driverRequest` — الذي لا يأتي.

## الإصلاح الصحيح بدل ما اقترحناه سابقاً

إعادة إرسال العروض المعلّقة عند الاتصال، **بلا أي لمس لـ`availability`**:

```js
// داخل driverNS.on("connection")، بعد socket.join(driverId.toString())
const pending = await Order.find({
  pendingDriverIds: driverId,
  driverSearchExpiresAt: { $gt: new Date() },
}).populate("restaurantId", "name address location");

for (const order of pending) {
  socket.emit("order:driverRequest", {
    // نفس حمولة startSearchRound
    secondsLeft: Math.max(
      0,
      Math.floor((order.driverSearchExpiresAt - Date.now()) / 1000),
    ),
  });
}
```

هذا يجعل جرس FCM مفيداً فعلاً: يوقظ التطبيق ← يتصل ← يستلم العرض بما تبقّى من وقته.
ويحل المشكلة بلا أي من الأضرار التي ذكرتموها.

**بديل مكمّل (اختياري):** توسيع حمولة FCM لتحمل العرض كاملاً ووقت انتهائه، مع بقاء القبول عبر السوكيت.

## ما نتفق عليه أيضاً

- **تسمية لوحة الأدمن:** «متاح» بدل «متصل» — موافقون تماماً، وهي في مستودعكم لا عندنا.
- **الـ sweep الدوري بـ`lastSeen`:** معالجة منطقية لسيناريو «غير قابل للوصول فعلياً»، ونؤجله كما اقترحتم.

## سؤال يحسم التنفيذ

هل تستطيعون إرسال **الوقت المتبقّي** (`secondsLeft` أو `driverSearchExpiresAt`) مع العرض؟
التطبيق يبدأ عدّاد ٣٠ ثانية من لحظة الاستلام، فإعادة إرسال عرض مضى نصف وقته ستعرض للسائق وقتاً
خاطئاً. وهذا يلتقي مع طلب سابق لنا: حمولة العرض لا تحمل أجر السائق ولا زمن الوصول المتوقع.

# ✅ راجعنا تنفيذكم — سليم ولا يحتاج شيئاً منّا (2026-09-13)

فحصنا الكتلة الجديدة في `driver.socket.js` مقابل `startSearchRound`، وكل نقطة ذكرتموها صحيحة:

- الحمولة مطابقة حقلاً بحقل، بما فيها `driverEarning` و`restaurantLocation`
  (شكل `location` في `models/restaurant.js` مطابق لما يبنيه `startSearchRound` يدوياً).
- `driverEarningOf` لا يحتاج إلا `originalDeliveryFee`/`deliveryFee`، وكلاهما ضمن `.select()`.
- قراركم بإعادة استخدام **نفس مفتاح `timeoutSeconds`** بقيمة الوقت المتبقي كان صحيحاً:
  التطبيق يقرأه فعلاً في `new_order_request_screen.dart` ويمرّره للعدّاد (مع طرح هامش أمان ثانيتين)،
  فالعرض المُعاد يظهر بوقته الحقيقي بلا أي تعديل عندنا. شكراً على الانتباه لهذه النقطة.
- شرط `availability === "online"` في محلّه، والإرسال المكرر لا يُربك السائق لأن التطبيق يتجاهل أي
  عرض جديد وهو داخل شاشة طلب.

## حالة واحدة عالجناها عندنا (لا عمل مطلوب منكم)

مكتبة السوكيت في التطبيق **تُخزّن** أي رسالة تُرسَل أثناء الانقطاع وتُفرّغها عند عودة الاتصال.
فإذا انتهى عدّاد العرض محلياً والسائق مقطوع، كان التطبيق يرسل `rejected` فيُخزَّن، ثم يصل في نفس
لحظة إعادة إرسالكم للعرض — فيسحب السائق من `pendingDriverIds` ويُغلق شاشة العرض برسالة «تم رفض
الطلب» وهو لم يرفض شيئاً. أي أن الحالة التي بُني لها B9 كانت ستُفسد نفسها.

أصلحناه في التطبيق: لا يخرج أي `order:driverResponse` والسوكيت مقطوع، ولا يُقفل قرار القبول عندها
أيضاً بل تبقى الشاشة وعدّادها ليحاول السائق فور عودة الشبكة. أضفنا ثلاثة اختبارات تغطي الحالتين.
